## 1. Architectural Mandate: The Zero-Leak Network Model

In conventional desktop operating systems (Windows, Linux, macOS), the kernel embeds a standard monolithic TCP/IP stack (IPv4/IPv6, ARP, DHCP, DNS). Whenever an application requests internet access, raw unencrypted packets leave the physical network adapter directly towards an ISP gateway. This exposes the user to:
* ISP-level logging, DNS hijacking, and SNI inspection.
* Fixed public IP tracking and geolocation profiling.
* Harvest-Now, Decrypt-Later (HNDL) state surveillance.
* Correlated traffic analysis via packet size and inter-arrival timing signatures.

### The KELLER-OS Paradigm Shift
**KELLER-OS has no native direct TCP/IP exposure.** The physical network interface (Ethernet, Wi-Fi, LTE, SDR) is strictly forbidden from transmitting raw IP traffic to an ISP. 

Instead, **[Vantablack (Global Ghost Net)](https://github.com/KELLERBABG/Vantablack)** constitutes the **exclusive, native Internet Access Layer** of KELLER-OS. Every outbound network byte generated by the kernel, shell, or graphical user interface is ingested by the Vantablack protocol engine, converted into **erasure-sharded, post-quantum encrypted privacy frames**, and routed across divergent peer carrier nodes across the global decentralized WAN mesh.

## 2. Core Vantablack Subsystems in KELLER-OS

### 2.1 Post-Quantum Hybrid Identity & The "Ghost Handshake"
* **Integration Point:** [`src/crypto.rs`](src/crypto.rs) (`PeerIdentity::build_handshake_blob`)
* **Mathematical Invariant:** Vantablack establishes peer sessions using hybrid **ML-KEM-768 / ML-KEM-512** (FIPS 203 Kyber) combined with **X25519 ECDH**.
* **Handshake Sharding:** The 960-byte binary handshake blob (`GHOST_HANDSHAKE_`) is encoded into two 480-byte data shards and one parity shard using Reed-Solomon $\text{RS}(2,1)$. Even during acute link degradation, any 2 shards arriving at a peer establish session keys without connection renegotiation.

### 2.2 ShardSec: Per-Shard Authentication
* **Problem:** In traditional erasure-coded networking, if a rogue intermediary carrier tampers with one shard in transit, the corruption is only discovered after full reconstruction fails, wasting cycles and masking the malicious node.
* **Vantablack Defense:** Under **ShardSec (default-on)**, every individual Reed-Solomon shard is sealed under its own HKDF-derived subkey with a dedicated Poly1305 authentication tag.
* **Kernel Verification:** If an adversarial or noisy carrier flips a single bit in Shard 1, the Poly1305 tag check fails instantly at the ingress pipeline. Shard 1 is discarded before entering reconstruction memory, and pristine plaintext is rebuilt from Shards 0 and 2.

### 2.3 Byzantine Tamper Isolation (Combinatorial Verification)
* When operating in zero-trust mesh topologies where intermediary carrier nodes may actively modify packets (`BYZANTINE_TAMPER=1`):
* The receiver executes **combinatorial pairwise testing**:
  * Test Pair $(0, 1)$ — evaluates without Shard 2.
  * Test Pair $(0, 2)$ — evaluates without Shard 1.
  * Test Pair $(1, 2)$ — evaluates without Shard 0.
* The pair matching valid ChaCha20-Poly1305 MACs pinpoints the exact compromised route, triggering automatic link severance and route recalculation.

### 2.4 Anti-Traffic Analysis (576-Byte Wire Quantization & Poisson Jitter)
* **Constant-Size Framing:** In contrast to clearnet MTUs which disclose payload characteristics, Vantablack frames are strictly **quantized to a uniform 576 bytes** on the wire.
* **Keyed Jitter Tail:** Each frame includes a dynamic $16..64$-byte hardware-entropy padding tail (generated via x86_64 `RDRAND`) authenticated as AEAD associated data.
* **Poisson Cover Traffic:** When the user is idle, synthetic decoy frames are injected at Poisson-distributed intervals, removing both packet-size and silence signals from external Deep Packet Inspection (DPI).

```### 3.1 Packet Offsets in Bare-Metal Kernel ([`src/net.rs`](src/net.rs))
The bare-metal kernel packet serialization in `src/net.rs` matches Vantablack's framing specification. Every frame is emitted at **exactly 576 bytes** (`WIRE_FRAME_LEN = BASE_SIZE + JITTER_MAX`), for data as well as handshake traffic:
```rust
pub const BASE_SIZE: usize = 512;
pub const JITTER_MAX: usize = 64;          // WIRE_FRAME_LEN = 576
pub const HANDSHAKE_ID: u8 = 255;          // 960-byte GHOST blob, 480-byte shard block
pub const COVER_ID: u8 = 254;              // synthetic decoy frame

// Fixed header field offsets
pub const OFFSET_MSG_ID: usize = 0;
pub const OFFSET_ORIG_LEN: usize = 1;
pub const OFFSET_SHARE_START: usize = 2;   // 33-byte Shamir share (authenticated)
pub const OFFSET_SHARE_END: usize = 35;
pub const OFFSET_COUNTER_START: usize = 35; // 8-byte big-endian message counter
pub const OFFSET_COUNTER_END: usize = 43;
pub const OFFSET_SHARD_START: usize = 43;  // start of the ShardSec record

// ShardSec record: index(1) || plain_len(2, BE) || nonce(12) || ciphertext || tag(16)
pub const SHARD_HEADER_LEN: usize = 15;
pub const SHARD_OVERHEAD: usize = 31;      // header + tag
pub const DATA_SHARD_LEN: usize = 448;     // 43 + 31 + 448 + 54 = 576
pub const MIN_TAIL_LEN: usize = 16;        // entropy tail bounds
pub const MAX_TAIL_LEN: usize = 64;

// Message budget: tag(16) || payload, zero-padded, Reed-Solomon RS(2,1) coded
pub const MESH_MESSAGE_MAX: usize = 896;
pub const MESH_PAYLOAD_MAX: usize = 880;
```

**Associated data per shard:** `header(43) || shard_index || plain_len || tail_len || tail`. The tail is drawn
from the DRBG on every frame and authenticated in full, so editing padding voids the frame exactly like
editing ciphertext.

**Message authentication:** each coded message starts with a 16-byte HMAC-SHA256 tag over
`msg_id || counter || orig_len || payload`, keyed by an HKDF-derived message key. ShardSec therefore
authenticates every shard *and* the reconstruction authenticates the message, which is the anchor the
combinatorial pairwise test scores against (see §2.3). Handshake frames carry no such tag: the
960-byte GHOST blob is signed by the peer's Ed25519 identity instead.

**Peer state:** `KellerNet` keeps one `PeerState` per remote node — identity fingerprint, its own
`KernelSessionGuard` replay window, tamper counters and an isolation flag. A peer that spends its
tamper budget (`shards_refused >= 3`) is severed until route recalculation calls
`rehabilitate_peer()`, which is the hot-swap path of §4 Scenario C.

### 3.2 Anti-Replay Session Guard Integration ([`src/session.rs`](src/session.rs))
Both the Vantablack daemon and the microkernel verify in-flight packet counters against the 128-bit sliding window bitmap (`KernelSessionGuard`), ensuring replayed mesh packets are rejected in constant time before decryption allocations occur. In the kernel the guard is **per peer**: the message counter is consumed by the first shard of a message, the remaining shards of that same message fold into the same window slot (they are position-bound by their ShardSec AAD, so a shard cannot be smuggled in twice), and a frame that arrives after the peer's window has moved on is dropped before any AEAD work is scheduled.

### 3.3 Physical Wire Transport — implemented, still ring 0

The transport the diagram above calls the sandbox's job is now real, with one deliberate difference:
it runs in **ring 0**. [`src/eth.rs`](src/eth.rs)
wraps each sealed 576-byte frame in Ethernet/IPv4/UDP (mesh port `0x4B4C`, probe port `0x4B4D`) and
[`src/nic.rs`](src/nic.rs) drives the
Intel 8254x (`e1000`) with 8 transmit and 8 receive descriptors over 4 KiB identity-mapped frames, so
the mesh's cover traffic, handshakes and data frames all leave the machine on a real segment, and a
peer's frames come back through the same `ingest_from` pipeline the loopback wire uses. The driver also
answers ARP for its own address: without that, a peer that has to learn the MAC (QEMU's user-mode
network, or any switched LAN) queues its replies behind a request nobody answers, and every counter
looks healthy while nothing arrives.

Why not ring 3 yet: a DMA-capable device behind a ring-3 task needs either an IOMMU or the
bounce-buffer split §1 describes — the sandbox decides, the kernel moves bytes. Handing a ring-3 task a
raw BAR today would hand it the whole physical address space, which is the opposite of the isolation it
would be sitting on. The plumbing that split needs is already in place (the rings are ordinary frames,
MMIO goes through one window, and the ports plus DMA addresses are the only things a grant would have
to cover), so the move is a sandbox boundary rather than a rewrite. Full design, the descriptor rules
that were bugs first, and the independent "[`dev- dev-tools/wire_check.py`](dev- dev-tools/wire_check.py)"
peer that validates every frame from the other end of the cable: [`NIC_WIRE.md`](NIC_WIRE.md).

### 3.4 Poisson Cover Traffic
Idle links are filled with decoy frames from `CoverTraffic`: one Bernoulli trial per 100 Hz tick with `p = 1 / interval`, which is a Poisson process sampled on the tick grid (a geometric waiting time in ticks, no floating point in the kernel). Each decoy is a real `COVER_ID` message — RS(2,1) split, ShardSec sealed, exactly 576 bytes — so decoys and user traffic are indistinguishable on the wire, and inbound decoys are counted as cover instead of being surfaced.

## 4. Internet Access Scenarios for KELLER-OS

### Scenario A: Sovereign Web Browsing & HTTP Requests
1. The user launches the GUI browser or runs `curl` in the `Keller Shell`.
2. The request routes to `127.0.0.1:1080` (Vantablack SOCKS5 proxy).
3. Vantablack splits the HTTP request into 3 erasure shards, encapsulates each shard with Kyber/X25519 hybrid keys, and dispatches them across 3 separate WAN carrier routes.
4. An autonomous **Vantablack Exit Node** reassembles the shards, decrypts the request, and proxies it to the clearnet destination (e.g. `httpbin.org`).
5. The response is encrypted, sharded, and returned across the mesh. The target server sees only the rotating egress IP (`198.51.100.x`), never the user’s real IP.

### Scenario B: Air-Gapped / Ad-Hoc SDR Mesh Communication
1. When no commercial internet or Ethernet connection is present, KELLER-OS utilizes Software Defined Radio (SDR) hardware managed in userspace.
2. Vantablack dispatches shards over radio frequencies (VHF/UHF/LoRa).
3. The $\text{RS}(2,1)$ forward error correction tolerates atmospheric noise and multi-path RF fading without requiring handshake packet retransmissions.

### Scenario C: Autonomous Self-Healing Failover
1. If an intermediary carrier link is severed or jammed, the `AdaptiveShardRouter` measures latency spikes via Poisson fitness metrics.
2. In $\le 55\text{ ms}$, the lost route is hot-swapped to an alternate standby carrier node with zero session termination and zero dropped TCP sockets.
